# Publishing ShiftVault on F-Droid and friends

This folder holds the submission package for the official F-Droid repository and
for the alternatives that are faster to get into.

- [`com.shiftvault.app.yml`](com.shiftvault.app.yml) — the fdroiddata build
  recipe, ready to be copied into a fork of
  [fdroiddata](https://gitlab.com/fdroid/fdroiddata).
- `../fastlane/metadata/android/` — the store listing F-Droid reads from the
  repository itself: title, short and full description, changelogs, icon and
  phone screenshots in `en-US` and `de-DE`.

## The one blocker: `android/` must be buildable from the repo

F-Droid builds every app from source in a sandbox; it never uses the APK from a
GitHub release. Right now `android/` is generated by
`npx cap add android` and ignored by Git, so a fresh clone only contains `www/`
and the build cannot run.

Two ways to fix it:

**Option A — commit the native project (recommended).** This is the standard
Capacitor workflow ("native projects as source") and the only variant that is
easy to reproduce offline:

```bash
npm ci
npx cap add android
node scripts/prepare-android.mjs   # icons, launcher aliases, native plugins
npx cap sync android
# then remove /android/ from .gitignore and commit the folder
```

Commit the *generated* `capacitor.settings.gradle`, `capacitor.build.gradle` and
`app/src/main/assets/public/` along with it; Gradle needs them at build time.
Keep `/android/build/`, `/android/app/build/`, `/android/.gradle/` and
`/local.properties` out of Git.

**Option B — generate in the recipe.** Add to `prebuild`:

```yaml
    prebuild:
      - npx cap add android
      - node scripts/prepare-android.mjs
      - npx cap sync android
```

This works, but it downloads the Gradle wrapper and the Capacitor template
during the build and is more likely to break on an F-Droid build server. Use it
only if Option A is not acceptable.

Either way, run `fdroid build com.shiftvault.app` locally (fdroidserver + a
Vagrant build VM) before submitting — the recipe here is a draft, not a verified
build.

## Submitting to F-Droid

1. Create a [Request for Packaging](https://gitlab.com/fdroid/rfp/-/issues) issue
   so the F-Droid team knows the app is coming.
2. Fork <https://gitlab.com/fdroid/fdroiddata>, create the branch
   `com.shiftvault.app` and copy `com.shiftvault.app.yml` to `metadata/`.
3. Push the recipe, tag the release (`git tag v1.0.0 && git push origin v1.0.0`)
   so the `commit:` in the recipe exists, and open a merge request titled
   `New app: ShiftVault` that links the RFP issue.
4. Answer review comments. Once the merge request is accepted, the F-Droid build
   server builds and signs the app; publication follows the next index update.

Expect weeks, not days. The recipe has to build on their build server, which is
the part that usually needs iterations.

## Faster: IzzyOnDroid and Obtainium

- **IzzyOnDroid** is a well-known F-Droid-compatible repository that adds apps
  from GitHub releases. Open an issue at
  <https://github.com/IzzySoft/IzzyOnDroid-inclusion> with the repository URL and
  the app is usually reviewed within days. Requirements: the APK must be on a
  GitHub release and signed with a key you control, and the app must be free of
  tracking — it is. See the signing note below.
- **Obtainium** needs no submission at all: users add
  `https://github.com/AeroBaden/ShiftVault` as a source and get updates straight
  from the GitHub releases. The README already mentions this.

## Signing

The release workflow currently publishes a debug-signed APK, which is fine for
sideloading but not for store distribution: IzzyOnDroid and Obtainium users
expect a stable signing key across versions, and a debug key is rejected or
warns on updates.

To publish properly signed releases, create one keystore and add four repository
secrets:

```bash
keytool -genkeypair -v -keystore shiftvault.jks -alias shiftvault \
  -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=ShiftVault"
base64 -w0 shiftvault.jks > shiftvault.jks.b64
```

| Secret | Value |
| --- | --- |
| `SIGNING_KEYSTORE_BASE64` | contents of `shiftvault.jks.b64` |
| `SIGNING_STORE_PASSWORD` | keystore password |
| `SIGNING_KEY_ALIAS` | `shiftvault` |
| `SIGNING_KEY_PASSWORD` | key password |

Keep `shiftvault.jks` itself out of the repository and backed up: losing it
means you can never update an installed app in place. The F-Droid build does not
need these secrets — F-Droid signs with its own key.
